# 领域资料

院内方剂有历史组方版本；临床资料、配制批次及质量检验由不同部门管理，原始患者资料不能混入公开资料。

`contracts/entities.json` 保存外部数据的首批交换字段。来源编号仅表示提交方对同一记录的识别符，示例文件不包含真实个人资料。运行时持久化文件由 `DATABASE_PATH` 决定；时间字段使用带时区偏移的 ISO 8601 字符串，重量统一以克记账。

## 质量放行链条与部门分工

来货批次（药库登记供应商凭证、产地、来货重量）→ 抽样与逐轮检验（检验人，复检为追加轮次，不覆盖首败）→ 来货处置判定（药事负责人）→ 分装/合批（药库，重量守恒）→ 开批与称量投料（配制负责人）→ 成品检验（检验人，不得是本批配制负责人）→ 成品放行（药事负责人，全链阻断复核）。

四类岗位角色：`warehouse`、`inspector`、`compounding_lead`、`qa_release`，接口按 `X-User-ID` 鉴权；签字互斥规则在应用层与 SQLite 触发器两处同时强制。检验读数、成品检验与放行决定均为追加式（数据库触发器禁止 UPDATE/DELETE），保证第一次失败读数与每次质量判断长期可查。

血缘方向为 成品批 ← 称量 ←（合批 ←）分装容器 ← 来货批次 ← 药材。放行复核与影响面查询都沿此图递归：不合格来货批次阻断其全部下游成品，`GET /v1/batches/{ref}/lineage` 支持从成品反查，`GET /v1/receipts/{ref}/impact` 支持从原料正向追踪。

`/public/v1` 下的外部查询不鉴权，且只暴露合格范围（`spec_min/spec_max/spec_unit`）与处置状态，不返回供应商凭证、产地、读数或签字信息。
